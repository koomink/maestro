Symphony 작동 구조: Maestro OS와 Virtuoso Apps

Symphony는 Maestro portfolio OS와 Virtuoso 전략 앱들의 생태계입니다. 이 문서는 Maestro의 운영 workflow, signal-to-approval handoff, account routing, Virtuoso 앱 계약을 탭으로 나누어 설명합니다.

Updated: 2026-05-28 Symphony = ecosystem Maestro = portfolio OS Virtuoso apps = strategy plugins app fragments = strategy-owned config accounts = operator-owned broker boundary KIS = broker adapter signal_run_id = approval handoff

한 문장으로 보기

Virtuoso 앱은 투자 제안을 만들고, Maestro는 그 제안을 데이터, 유니버스, 위험 한도, 승인, 브로커 상태와 대조한 뒤 실행하거나 멈춥니다.

핵심 원칙: Virtuoso apps propose. Maestro decides. Maestro protects. Maestro executes. Maestro records.

현재 Operator Topology

최신 Symphony 운영 구조는 전체 YAML을 앱 repo가 복사해 들고 있는 방식에서 벗어나, Maestro operator profile이 계좌, 승인, 실행, 상태를 소유하고 Virtuoso 앱은 fragment로 전략 고유 정보만 제공합니다.

symphony_readonly

계좌 관찰 전용

configs/operator/symphony_readonly.yaml은 broker snapshots, reconciliation, dashboard/Telegram read commands의 shared truth를 갱신합니다. 전략 signal이나 주문 제출은 하지 않습니다.

symphony_signal

전략 실행과 signal package

configs/operator/symphony_signal.yaml은 enabled Virtuoso apps를 실행해 signal_package, account mapping, broker snapshot refs, DataHub evidence, order preview를 저장합니다.

symphony_approval

저장된 signal 승인

configs/operator/symphony_approval.yaml은 전략을 다시 실행하지 않고 signal_run_id를 소비합니다. 만료, config drift, broker snapshot drift, safety/reconciliation failure는 fail-closed입니다.

Run-once Workflow

maestro run-once는 단일 profile을 한 번 실행하는 기본 cycle입니다. Symphony operator flow는 이 원리를 run-signal과 approve-signal로 나누어, 전략 실행과 승인 실행을 분리합니다.

1. Config loadoperator YAML, mode, profile_stage, state/audit path
2. Plugin loadVirtuoso app entrypoint and SDK contract
3. Data requestsDataRequest objects through Maestro DataHub
4. Strategy resultTargetAllocationResult or normalized signal
5. Validationstrategy id, symbols, research/tradable boundary

↓

6. Portfolio targetcombine weighted strategy proposals
7. Risk gatecash, exposure, order count, broker risk checks
8. Order proposalpaper proposal engine creates limit order intents
9. Approval gateconsole or Telegram approval where required
10. Execute & recordpaper fill or live approval lifecycle, SQLite, audit JSONL

Signal-to-Approval Handoff

최신 Symphony operator flow는 관찰, 신호 생성, 승인 실행을 분리합니다. symphony_signal이 전략을 실행해 immutable signal_run_id를 만들고, symphony_approval은 그 signal package를 소비할 뿐 전략을 다시 실행하지 않습니다.

1. Read-only refreshsymphony_readonly가 broker snapshots와 reconciliation evidence를 갱신
2. Signal runrun-signal이 Virtuoso apps, DataHub evidence, risk preview, order preview를 저장
3. Signal packageconfig identity, account mapping, broker snapshot refs, data freshness, preview orders 포함
4. Approval runapprove-signal이 저장된 signal을 검증하고 Telegram approval을 생성
5. Lifecycle승인된 주문만 dry-run event 또는 live order lifecycle로 진행
Approval은 signal 만료, config fingerprint mismatch, strategy-account mapping drift, stale broker snapshot, missing/stale DataHub evidence, reconciliation 실패를 모두 fail-closed로 거부합니다.

Mode, Order, Broker, Account Type

운영 config가 헷갈리는 이유는 네 가지 축이 한 파일에 같이 있기 때문입니다. 각각은 같은 의미가 아니라 서로 다른 질문에 답합니다.

Mode

이 run이 어디까지 들어갈 수 있나

paper, live_readonly, live_approval처럼 Maestro workflow의 큰 안전 계약을 정합니다. 전략 실행, approval 필요 여부, broker snapshot 사용 여부가 여기서 갈립니다.

Order posture

주문 후보가 실제 submit까지 갈 수 있나

disabled는 주문 제출 차단, dry_run은 승인까지 연습하되 broker submit 생략, armed는 승인 후 submit 가능 상태입니다.

Broker boundary

어느 외부 시스템에 닿나

PaperExecutionEngine은 내부 state만 바꾸고, KIS read-only는 계좌를 읽기만 하며, KIS live approval은 승인된 limit order를 KIS로 보냅니다.

Account type

KIS가 모의투자인가 실계좌인가

kis.paper_trading=true는 KIS 모의투자 서버를 뜻합니다. Maestro의 mode: paper와 다르며, KIS 모의계좌도 실제 broker API 경계를 탑니다.

질문 보는 설정 쉬운 해석
전략을 돌리는가? mode, strategies[].enabled live_readonly는 전략을 돌리지 않고, live_approval은 enabled 전략을 실행합니다.
주문 후보를 실제로 제출할 수 있는가? execution.order_posture disabled와 dry_run은 broker submit을 막고, armed만 submit을 허용합니다.
KIS 계좌를 읽는가, 주문도 보내는가? kis.enabled, broker product, live order client KIS read-only는 account truth를 가져오고, KIS live approval은 승인된 주문 lifecycle까지 담당합니다.
모의투자인가 실계좌인가? kis.paper_trading true면 KIS 모의투자, false면 실계좌 경로입니다. 둘 다 Maestro paper mode와는 다릅니다.
핵심 구분: live_readonly는 계좌를 읽기만 하는 관찰 모드이고, live_approval + order_posture=disabled는 전략과 approval 구조는 켜되 최종 주문 제출만 차단한 리허설 상태입니다.
다음 운영 구조: 목표 workflow는 symphony_readonly로 계좌 상태를 읽고, symphony_signal로 Virtuoso 전략을 실행해 immutable signal_run_id를 만들며, symphony_approval이 그 signal을 재사용해 approval과 주문 lifecycle을 진행하는 구조입니다. approval 단계에서는 전략을 다시 실행하지 않으며, deployment wrapper는 actionable signal일 때만 approval phase를 호출합니다.
Current Symphony handoff systemd timer → maestro daily-signal-approval --readonly-config configs/operator/symphony_readonly.yaml --signal-config configs/operator/symphony_signal.yaml --approval-config configs/operator/symphony_approval.yaml → read-only broker refresh and reconciliation → signal_package(signal_run_id) → Telegram daily signal summary → if actionable: stop telegram operator while approval consumes shared bot polling → per-strategy Telegram approval requests → restart telegram operator

DataHub Boundary

DataHub는 전략이 시장/리서치 데이터를 요청하는 유일한 통로입니다. Provider는 교체 가능하지만, 전략 앱은 yfinance, FRED, NewsAPI, KIS 같은 외부 API를 직접 호출하지 않는 것이 원칙입니다.

Allowed path

전략 데이터 흐름

Virtuoso Strategy → DataRequest → Maestro DataHub Router → yahoo / csv / fred / rss / gdelt / newsapi provider → normalized DataBundle → StrategyResult
Blocked idea

피해야 할 흐름

Virtuoso Strategy → direct yfinance call → direct KIS quote call → direct Telegram or broker call
KIS quote/reference data는 live approval의 주문 가격 검증이나 reconciliation 보조로 사용할 수 있지만, 전략 리서치 데이터의 주 소스로 삼지 않습니다.

Broker Execution Boundary

Broker adapter는 계좌와 주문의 세계입니다. DataHub가 “무엇을 살지 판단할 데이터”라면, KIS adapter는 “실제 계좌 상태와 주문 제출/조회/체결을 다루는 경계”입니다.

KIS adapter는 국내/해외 상품별 차이는 유지하되, 인증, base URL, request/response 처리 같은 REST 공통부는 shared base client로 모았습니다. Instrument의 broker_product가 kis_domestic_stock 또는 kis_overseas_stock adapter 선택을 결정합니다.
경로 무엇을 하나 무엇을 하지 않나
PaperExecutionEngine Maestro 내부 state에서 주문 체결을 시뮬레이션합니다. KIS 계좌나 KIS 모의투자 서버에 주문을 보내지 않습니다.
KIS read-only 잔고, 포지션, buying power, 체결/미체결, current price reference를 읽습니다. 주문 submit, cancel, amend를 하지 않습니다.
KIS live approval 승인 후 limit order submit, status polling, fill reconciliation을 수행합니다. live_auto, market order, direct buy/sell/cancel CLI를 제공하지 않습니다.

Multi-account Broker Routing

Symphony operator profile은 top-level accounts와 공유 strategy_account_map_path로 전략별 계좌를 분리합니다. 하나의 enabled Virtuoso app은 정확히 하나의 logical account에 매핑되고, 여러 전략은 같은 계좌를 공유할 수 있습니다.

운영 서비스와 공유 상태

현재 Maestro는 하나의 상시 데몬이 아니라, 여러 CLI job과 long-running service가 같은 operator config, SQLite state DB, JSONL audit log를 공유하는 hybrid operator architecture입니다.

One-shot CLI

짧게 실행되는 명령

  • run-once: 전략 cycle 실행
  • run-signal: signal package와 signal_run_id 생성
  • approve-signal: 저장된 signal을 승인/주문 lifecycle로 전달
  • kis-sync: broker snapshot 저장
  • reconcile: Maestro state와 broker truth 비교
  • health, live-preflight: readiness 확인
Long-running

계속 떠 있는 서비스

  • telegram-operator: 읽기 전용 명령과 제한된 pause/kill
  • dashboard: read-only FastAPI/React UI
  • systemd timer/service: readonly refresh, signal handoff, heartbeat
Shared truth

공유 저장소

  • SQLite state: portfolio, orders, events, broker snapshots
  • JSONL audit: append-only operational trail
  • Config fingerprint: app fragment, account map, state-affecting 변경 감지

Dashboard Operator Console

Dashboard는 Streamlit식 raw table 화면이 아니라, FastAPI backend와 React editorial report frontend로 구성된 read-oriented operator console입니다. 첫 화면은 실제 Daily Brief이며, Analysis Report, Virtuoso, toggle 가능한 Console drawer로 운영 상태를 읽고 AI에게 넘길 diagnostic context를 복사할 수 있습니다.

Broker Truth

Multi-account overview

Daily Brief의 Broker Truth는 마지막 snapshot 하나가 아니라 enabled broker account별 최신 상태를 보여줍니다. KIS/Toss 같은 실제 broker 계좌는 fresh/stale/missing으로 표시하고, sandbox 계좌는 broker truth 대상에서 제외합니다.

Global Refresh

계좌와 freshness 갱신

상단 Refresh는 symphony_readonly config로 broker/account snapshot을 갱신하고 최신 signal freshness를 분류합니다. Virtuoso app을 실행하지 않고, approval이나 order도 만들지 않습니다.

Virtuoso tabs

Overview + app별 signal

Virtuoso 탭은 전체 전략 상태를 보는 Overview와 app별 하위 탭으로 나뉩니다. app별 Generate Signal은 symphony_signal config로 선택된 전략 하나만 실행해 proposal signal을 저장합니다.

Safety boundary

주문 실행 버튼이 아님

Dashboard action은 계좌 refresh와 proposal-only signal generation까지입니다. Telegram approval, broker submit, recovery, kill-switch 같은 trading/admin action은 Dashboard에 두지 않습니다.

maestro dashboard \ --config configs/operator/symphony_readonly.yaml \ --signal-config configs/operator/symphony_signal.yaml \ --host 127.0.0.1 \ --port 8503
Dashboard는 계좌 정보와 운영 상태를 보여주므로 기본은 127.0.0.1 바인딩입니다. Mac에서 원격 서버의 Dashboard를 볼 때는 공개 0.0.0.0 노출보다 SSH port forwarding을 사용합니다.

권장 Promotion Path

지금 프로젝트 방향인 “Mock data → Real Data”와 “Maestro paper → KIS 모의투자” 전환은 아래 순서로 나누면 가장 안전합니다.

단계 목표 확인해야 할 것
1. paper MockDataHub와 PaperExecutionEngine으로 기본 cycle 검증 plugin loading, target allocation, risk decision, paper orders, audit
2. paper_real_data Yahoo/yfinance 등 실제 DataHub provider로 가격/OHLCV 전환 symbol_map, freshness, stale/missing data behavior, no direct strategy API calls
3. live_readonly KIS 계좌 snapshot과 reconciliation 검증 cash, positions, buying power, current prices, state adoption boundary
4. live_approval_dry_run 승인과 lifecycle 경로를 통과하되 broker submit은 건너뜀 Telegram approval, safety gates, proposal snapshot, dry-run event
5. kis_paper_trading KIS 모의투자 계좌로 approval-gated limit order submit status polling, fill reconciliation, broker reconciliation, recovery runbook
6. production_armed 실계좌 approval-gated 최소 주문 beta-preflight, loss limits, audit integrity, heartbeat, backup/restore

안전 장치

Maestro는 의도적으로 자동 거래 시스템이 아닙니다. 실계좌 자동화를 서두르기보다, 승인과 상태 기록, 회복 절차를 먼저 단단하게 둡니다.

계속 유지하는 금지선

  • live_auto 없음
  • market order 없음
  • direct buy/sell/cancel CLI 없음
  • dashboard trading/admin controls 없음
  • dashboard action은 read-only refresh와 proposal-only signal generation까지만 허용
  • 전략 앱의 broker/API 직접 호출 없음

주요 gate

  • Safety state: active, paused, killed, halted
  • Telegram approval required in live_approval
  • Limit order only
  • Reconciliation freshness
  • Daily notional/order count/loss limits
  • Unknown broker state halt

Virtuoso Apps 한 문장 요약

Virtuoso 앱은 전략별 사고와 제안을 담는 외부 패키지입니다. 앱은 candidate instrument, data need, target allocation 또는 signal을 제안하고, Maestro는 데이터 접근, 유니버스 승인, 위험 관리, 승인, 실행, 상태, 감사를 소유합니다.

핵심 경계: 전략 특화 코드는 Virtuoso 앱 repo에 있고, Maestro core에는 SDK 계약과 실행/검증/운영 spine만 둡니다.

앱 계약과 Loader Boundary

Maestro는 strategies[*].entrypoint로 앱을 로드합니다. 앱은 maestro.sdk만 Maestro 의존성으로 사용해야 하며, broker, state, approval, Telegram, DataHub internals를 직접 import하지 않습니다.

Manifest

앱의 신분증

  • strategy_id가 config id와 일치해야 합니다.
  • 지원 mode와 asset type을 선언합니다.
  • can_run_live 없이는 live approval에서 실행하지 않습니다.

현재 Symphony workspace에는 성격이 다른 Virtuoso 앱들이 있습니다. 공통점은 모두 Maestro SDK로 제안만 하고, 실행/계좌/주문/감사는 Maestro가 맡는다는 점입니다.

App이 소유하는 것과 소유하지 않는 것

Virtuoso 앱은 투자 아이디어와 전략별 계산을 소유합니다. 하지만 운영 위험이 큰 부분은 Maestro가 중앙에서 통제합니다.

Virtuoso App owns

전략 고유 영역

  • 전략 파라미터와 내부 알고리즘
  • candidate symbol/data need 제안
  • 목표 allocation 또는 signal 산출
  • LLM/model 선택과 strategy-specific dependencies
  • 앱 repo 안의 adapter와 contract tests
Maestro owns

운영/자본 경계

  • DataHub provider routing, freshness, audit
  • tradable universe approval
  • portfolio construction and risk gates
  • Telegram/human approval
  • paper/KIS execution, reconciliation, recovery
  • SQLite state, JSONL audit, dashboard

App 개발 Workflow

새 앱은 Maestro repo 안에 직접 섞기보다, 앱 repo에서 wrapper를 만들고 Maestro runtime에 설치하는 방식이 권장됩니다.

maestro init-virtuoso-app \ --output ./my_app \ --package-name my_virtuoso_app \ --class-name MyVirtuosoStrategy uv pip install -e /path/to/Maestro uv pip install -e ./my_app
1. Scaffold

SDK contract로 시작

BaseStrategyPlugin, manifest, data request, run method, contract test를 생성합니다.

2. Paper first

실행은 작게

새 앱은 기본적으로 supported_modes=["paper"], can_run_live=false에서 시작합니다.

3. Promote

운영 profile로 승격

real DataHub, live_readonly, dry-run, KIS paper trading 순서로 Maestro profile을 통해 승격합니다.

Config Fragment 관점

앱은 전체 operator YAML을 소유하지 않고, app_fragment_paths로 전략 fragment를 제공합니다. broker, approval, execution, state, audit, promotion gate와 account binding은 Maestro/operator profile 책임입니다.

app_fragment_paths: - /path/to/my_virtuoso_app/configs/fragments/my_app.yaml strategy_account_map_path: strategy_accounts.yaml strategies: - id: my_virtuoso_app enabled: true weight: 1.0
Ataraxia fragment

앱 repo가 제공하는 것

Virtuoso/Ataraxia/configs/fragments/ataraxia.yaml은 Ataraxia entrypoint, KRW sleeve, TIGER/KODEX instrument metadata, Yahoo symbol-map hints, buy-only contribution recommendation을 제공합니다.

Operator overlay

Maestro가 결정하는 것

monthly_budget, buy_day, KIS account env vars, Telegram allowlists, live order limits, state/audit paths, and order_posture are operator-owned and stay out of app fragments.

앱 fragment는 전략 entrypoint, strategy defaults, DataHub needs, signal_to_allocation policy 정도로 제한하는 것이 안전합니다. KIS 계좌, Telegram allowlist, 주문 한도, state/audit path는 operator-local config가 소유해야 합니다.

Virtuoso Apps의 현재 과제

Maestro의 현재 방향이 real DataHub와 KIS 모의투자 계좌로 이동하는 만큼, Virtuoso 앱들도 “직접 호출하지 않고 Maestro 경계를 통과하는 방식”을 더 단단히 해야 합니다.

가까운 과제

  • KR+US multi-account operator config에서 symbol_map, broker_product, freshness 검증
  • Ataraxia run-signal → approve-signal dry-run rehearsal
  • Snowball strategy book performance와 account-scoped dashboard attribution 검증
  • TradingAgents의 operator mapping 후보화 전 LLM/API credentials와 DataHub payload audit 정리

계속 지킬 원칙

  • 전략 앱은 주문을 제출하지 않습니다.
  • 전략 앱은 KIS 계좌를 읽지 않습니다.
  • 전략 앱은 외부 market/news API를 직접 호출하지 않습니다.
  • live approval 승격은 Maestro의 preflight와 operator 승인 뒤에만 진행합니다.
