## 원인 — 락 순서 역전

`writer_lock`과 `live_order_lock`을 **반대 순서로** 잡는 경로가 공존한다. 프로세스가 다르면 교착이고, 두 락 모두 10초 타임아웃이 있어 영구 정지 대신 `TimeoutError`로 나타난다 — 관측된 현상과 일치한다.

### 확인된 역순 경로

| 경로 | 획득 순서 |
|---|---|
| `Orchestrator.resolve_pending_signal_approval` (`orchestrator.py:304`) → 집행 중 이벤트 기록 | `live` → `writer` |
| `Orchestrator.approve_signal` (`orchestrator.py:289`) → `_approve_signal_locked` → `_execute_live_approval_orders` → `submit_approved_order` (`live_order_safety.py:47`) | **`writer` → `live`** |
| `Orchestrator.dispatch_signal_approval` (`orchestrator.py:295`) | `writer` → (집행 없음) |
| `PartialFillReconciliationService.reconcile_latest` (`live_order_fills.py:35-36`) | **`writer` → `live`** |

> **1차 스펙의 오류 두 가지를 정정한다.**
> 1. 1차는 "집행 경로는 live→writer이므로 그것을 정본으로 삼는다"고 했으나, **`approve_signal`은 writer를 쥔 채 live로 내려간다.** 역전은 체결 대조와 집행 사이만이 아니라 **오케스트레이터의 두 진입점 사이에도** 있다. 정본 순서를 "집행이 하는 대로"로 정할 수 없다.
> 2. 1차는 `cli.py:486/1259/1659`를 `PartialFillReconciliationService` 호출자로 인용했으나 **다른 대조 서비스**의 호출이다. 호출자 목록이 부정확했다.
>
> 또한 "한 프로세스 안에서는 재진입이라 안전하다"는 서술도 정확하지 않다. 재진입 카운터는 **thread-local**(`store.py`의 `_lock_depths`)이므로 같은 프로세스라도 **다른 스레드**에는 적용되지 않는다.

### 증거의 한계

`writer_lock`은 `owner` 인자를 받고 **즉시 버린다**(`store.py:290`의 `del owner`). 락 파일에 보유자·PID·획득 시각이 남지 않아 이번 사고에서 **누가 10초를 붙잡았는지 증명할 수 없었다.** 위 진단은 코드 구조와 정황의 일치에 근거하며, 보유자 기록으로 확정한 것이 아니다.

## 이 스펙의 범위 — 1부만 다룬다

1차 개정 뒤 작업이 **세 개의 독립 시스템**으로 커졌다. 하나의 스펙·계획으로 묶으면 검증 표면이 지나치게 넓어지므로 분할한다.

| 부 | 내용 | 상태 |
|---|---|---|
| **1부 (이 문서)** | 락 순서 정합성 + 계측 | 지금 구현 |
| 2부 | 당일 재계산·재승인 복구 흐름 (세대 펜싱 포함) | 별도 스펙 |
| 3부 | 취소 상태 머신 (terminal 증거, 브로커별) | 별도 스펙 |

1부를 먼저 하는 이유: **사고의 직접 원인이고**, 2·3부가 만드는 새 경로들도 같은 락 위에서 돌기 때문이다. 순서를 고치지 않은 채 복구 흐름을 얹으면 그 흐름 자체가 같은 교착에 빠진다.

2·3부의 요구사항은 아래 "이월" 절에 리뷰 지적과 함께 남긴다.

## 설계 (1부)

### 1. 정본 락 순서를 정하고 전이 경로까지 맞춘다

**정본: `live_order_lock` → `writer_lock`.**

근거는 "집행이 그렇게 한다"가 아니라(그 근거는 위에서 무너졌다) **`live_order_lock`이 더 바깥에서 더 오래 잡히는 자원**이기 때문이다. 주문 제출·체결 대기는 수 분이 걸리고 그동안 여러 번의 짧은 쓰기가 필요하다. 반대로 두면 긴 작업이 짧은 락을 계속 재획득하는 동안 바깥 락을 쥔 다른 프로세스와 엇갈린다.

따라서 **`writer_lock`을 쥔 상태에서 `live_order_lock`을 요구하는 경로를 전부 없앤다.** 대상은 위 표의 `approve_signal`, `dispatch_signal_approval`(집행으로 내려가는 경우), `PartialFillReconciliationService.reconcile_latest`이며, 호출 그래프를 훑어 **전이적 획득까지** 목록화한 뒤 고친다.

### 2. 위반을 런타임에 즉시 드러낸다

두 락을 함께 잡는 곳이 순서를 지역적으로 고르지 못하게, `StateStore`에 **두 락을 정본 순서로 함께 잡는 단일 API**를 두고 개별 획득을 대체한다.

그것만으로는 전이 경로를 막지 못하므로(호출자가 이미 `writer`를 쥐고 내려올 수 있다), **런타임 순서 검증**을 넣는다: `writer_lock`을 보유한 상태에서 `live_order_lock`을 요구하면 **즉시 예외**를 던진다. 조용한 교착 대신 개발·테스트 단계에서 위반이 드러난다.

### 3. 락 계측 — 다음 사고를 증명 가능하게

두 락이 `owner`를 버리지 않고 기록하게 한다. 락 파일에 **보유자·PID·획득 시각**을 쓰고, 타임아웃 시 예외 메시지와 이벤트에 **그때의 보유자**를 담는다. 대기 시간이 임계치를 넘으면 그 사실도 남긴다.

## 검증 (1부)

- **순서 위반 부재**: 런타임 검증을 켠 채 전체 스위트를 돌려 위반이 하나도 발생하지 않음을 확인한다. 위반 검출 자체도 테스트로 고정한다(고의로 역순을 만들면 예외가 난다).
- **교착 부재**: **두 프로세스**가 각각 집행과 체결 대조를 동시에 시도해도 교착·타임아웃이 없음을 확인한다. 재진입 카운터가 thread-local이므로 **다중 스레드** 경우도 별도로 확인한다.
- **계측**: 타임아웃 시 예외·이벤트에 보유자와 대기 시간이 실제로 담기는지 확인한다.
- **회귀**: 전체 스위트(`pytest tests/ -q`)와 `ruff check src tests`.

## 이월 — 2부·3부 요구사항 (리뷰 지적 보존)

### 2부: 당일 복구

- 목표 비중 전략이므로 **낡은 수량을 재제출하지 않는다.** 최신 브로커 포지션·현금·가격을 다시 읽고 잔여 목표를 재계산해 **새 승인**을 요청한다.
- 다음 정기 런까지 미루지 않는다. US 신호는 평일 1회이므로 금요일 사고나 halt 지연이면 미배치가 여러 날 이어진다. 완료 기한과 미완료 반복 알림·에스컬레이션을 정의한다.
- **세대 펜싱이 필수다.** 중단 건별 `recovery_group_id`와 단조 증가 generation을 영속화하고, 활성 generation 하나만 원자적으로 claim한다. 새 generation 생성 시 이전 미결 승인을 폐기하고, 승인 실행 직전에 동일 generation·동일 broker snapshot·원주문 상태를 재검증한다. 현재 주문 멱등 키는 `signal_run_id`·`order_intent_id`에 묶이므로, 재계산이 새 run을 만들면 **두 복구 승인이 서로 다른 키를 얻어 각각 집행될 수 있다** — 이 펜싱이 없으면 이중 집행이다.

### 3부: 취소 종결

- **스냅샷에서의 부재는 terminal 증거가 아니다.** KIS 개별 조회는 일일·미체결 조회에서 찾지 못하면 `UNKNOWN`을 반환하므로, API 지연·조회 범위 불일치·이력 이동으로 인한 부재와 실제 CANCELED/FILLED를 구분하지 못한다. 종결 증거는 **주문 이력의 명시적 CANCELED/FILLED/REJECTED와 누적 체결 수량 대조**로 제한하고, 부재는 UNKNOWN으로 유지한다.
- **브로커 취소 API에 idempotency key가 없다.** `LiveOrderCancelRequest`와 Toss/KIS 취소 경로 어디에도 없으므로, 같은 로컬 키로 POST를 반복하는 것은 안전한 재시도가 아니다. 불확실 응답 뒤에는 먼저 상태·체결 이력을 조회하고, 여전히 OPEN일 때만 브로커별 재시도 정책을 적용한다.
- `LiveOrderCancellationService.cancel_order`(`live_order_cancellation.py:25`)는 현재 브로커 응답을 기록할 뿐 terminal 재조회도 경쟁 체결 대조도 하지 않으며, `_is_duplicate_cancel`이 같은 주문의 재시도를 **일괄 거부**한다. 이를 단일 상태 머신으로 통합한다.
- 조회 기한 초과·익일 이력 이동처럼 **자동으로 종결할 수 없는 상태**를 정의하고, 그 경우 수동 증빙 경로로 보낸다.
- `pending_broker_orders` 차단과 `clear-halt`는 이 종결 확인 뒤에만 풀린다. 차단 자체는 유지한다 — 미체결이 있으면 포지션 인식이 불확실하고 그 위에 새 주문을 얹으면 이중 매매가 된다.
